reivew-prototype / design · issue #6 readable findings · 2026-10-09

Review styles: findings a person can judge and an AI can fix

Posted review comments were accurate but hard to judge: a person could not tell quickly why the reviewer asked for a change, or whether it was real. Findings now come in plain-word parts with the evidence folded underneath, and you can pick how reviews are written on the status page. This page records what we found, what we tried, what it costs, and what we picked.

default: New skill + new format Caveman + new format Caveman + old format pick on the status page

01The problem (issue #6)

"When a human tries to assess a requested change, they can't even tell why the AI requested it."

We checked the system and 88 inline comments it had posted. The complaint held up, for three reasons:

What a finding looked like

  • One free-text body per finding: problem, impact and fix mixed in one paragraph
  • Median 472 characters, up to 1,511, dense with function and variable names
  • The effect on users was buried, or missing
  • No separate evidence: nothing said what the reviewer read to reach the claim
  • A guess and a proven bug looked the same

Why

  • The prompt began with /caveman:caveman-review, a skill whose rules are "one line per finding: location, problem, fix" and "drop restating what the line does"
  • The prompt asked for the opposite ("explain each problem and the fix"), so Claude compromised: long, but compressed
  • The output schema had one text field, so nothing forced the parts apart

02Formats we looked at

Five shapes, each tried on the same real finding (PR #1929, F1: the Stop button may not stop a request).

Will an AI fixer still understand it? Yes. AI tools read PR comments through the GitHub API as raw markdown, so the folded part is plain text to them. The labels mark which part is the instruction (Fix) and which is the reasoning (Why). The one rule that keeps this working: the Fix and Why parts must keep exact file, function and variable names.

03The new format

Each finding is six fields in the structured output. Our code lays them out, so the layout costs no tokens and the skill cannot break it.

FieldShown asRule
titleF1 · 🔴 bug: Stop button may not stop the requestPlain words, the effect, no code names
problemWhat's wrongOne or two plain sentences, no code names
impactWhat happens if not fixedWhat a user sees or what breaks. For a nit: say nothing breaks and why it still matters
fixFixExact files, functions, variables
suggestion (optional)GitHub suggestion boxExact new code for lines line..endLine; only when the whole fix is inside those lines and applying it alone leaves the code working
why▶ Why I think so (folded)Short bullets of what was read or traced, with exact names; says what was not verified
  • Suggestion safety in code: a suggestion replaces exactly the lines the comment covers. If a range finding's end line is not in the diff, the comment falls back to one line, and the suggestion box is dropped (the Fix text stays).
  • Findings off the diff go in the review body under a #### F2 · 🟡 risk: title heading with the same parts, never with a suggestion box.
  • Old reviews keep working: findings saved with one body show exactly as before, on GitHub, in review.md and on the status page.
  • The field is named why, not evidence, because round-two verdicts already have an evidence field, and the ledger strips it between rounds.

The new skill (plugin/skills/readable-review/SKILL.md, about 2.3 KB; caveman's is 2.8 KB) is just a text file of writing rules: who reads a finding (a person who may not know the code, and the author or their AI tool), how to write each part, what the severities mean, and what to avoid. It is loaded the same way caveman is, through the first line of the prompt. No new program or service.

05The test and its cost

PR #2023 (68 files, +4398 / −383), same commit cf0200b, Opus 5.5, high effort, dry run, nothing posted. One run per style.

Read these numbers with care. One run each. The three runs found different problems and read different amounts of code; both new-format runs read about twice as much. Most of the cost is Claude reading the code, not the skill or the format. The gap between the two new-format runs is mostly output tokens, and that run also wrote more findings and more suggestions. Run each style two or three more times before treating the percentages as fixed.

For scale: the 25 reviews saved before this test used 100k–4.5M input tokens and 3k–31k output tokens, $0.34–$2.96 each.

Each run found different things

  • Only the old-format run caught the DIFFERENT RELATIONSHIPS bypass (a bug).
  • Only Caveman + new format caught the spaced-arrow bypass.
  • Only New skill + new format caught the control-character bypass and pattern comprehensions.

That variation comes from the model, not the format. It's also why one run per style can't settle quality.

06Real examples

From the PR #2023 runs: the same nit in the old and new format, then a Caveman + new format risk.

Caveman + old format

F4 · 🔵 nit The comment says "cancel" and "payment_method_update" are both accepted. BillingPortalFlowSchema is z.enum(["payment_method_update"]), so only one value is valid. Fix the comment so it matches the schema.

New skill + new format

F4 · 🔵 nit: A test comment names an allowed value that the server actually rejects

What's wrong: The comment says both "cancel" and "payment_method_update" are accepted. The request schema accepts only "payment_method_update".
What happens if not fixed: Nothing breaks. A reader may assume a "cancel" flow exists and write a client or test against it.
Fix: Change the comment to say that only "payment_method_update" is accepted.

Suggested change
  // Rejected at validation, before any Stripe call: only
  // "payment_method_update" is accepted.
Why I think so
  • schemas/api-gateway/src/billing.ts: BillingPortalFlowSchema = z.enum(["payment_method_update"])
  • createBillingPortalSession types flow as "payment_method_update" only
Caveman + new format

F2 · 🟡 risk: Repeated path groups slip through when the arrow is written with spaces

What's wrong: The check for a repeated path group like ((a)-->(b))+ only spots arrows whose dashes touch each other. Writing ((a) - - > (b)){1,100} is not seen as a path, so the query is allowed.
What happens if not fixed: One query can make ArcadeDB list every path up to 100 hops. That is the memory or CPU blow-up this PR exists to stop, and it hits every knowledge graph on the server.
Fix: In hasQuantifiedGroup, remove whitespace from group before testing it against RELATIONSHIP_ARROW.

Suggested change
    if (!isFunctionCall && RELATIONSHIP_ARROW.test(group.replace(/\s+/g, "")))
      return true;
Why I think so
  • RELATIONSHIP_ARROW (L195): the bare-arrow forms need the characters to touch
  • QUANTIFIED_RELATIONSHIP already allows spaces, so the two checks disagree
  • I did not run this against ArcadeDB.

Caveman did not break the new format: titles and impact stayed plain in both new-format runs.

07What we picked and why

Default: New skill + new format

  • The writing rules are ours and match the format; no "one line" rule pulls the other way
  • In the test it gave the most findings and the most suggestion boxes
  • It cost the most in the one run we measured ($1.99, against $1.49 and $1.20)

Kept as choices

  • Caveman + new format: the same readable layout for less output; pick it to save cost
  • Caveman + old format: exactly how reviews were written before issue #6; pick it to compare, or if the new format causes trouble

08How to switch

  • Status page (localhost:4777): the Style picker next to Model and Effort. It works like them: it applies from the next review on, a running review keeps its style, and the pick is saved in data/state.db, so it survives restarts.
  • Config default: "review": { "style": "readable" } in config.json. A pick on the status page wins over it.
  • Caveman location: review.pluginPath is now the caveman plugin folder; null finds the installed caveman@caveman. The new skill needs nothing installed.
  • Startup checks: the default style must be usable or the server won't start. The other styles are checked too, but only warn. Without caveman installed, the two caveman styles fail if picked.
  • Mixing rounds works: round one can use one style and round two another. Each finding is shown, and handed to Claude, in its own shape.
  • Each saved review records its style in result.json, and the status page shows it in the review detail.

10Caveats and open points

  • Read a suggestion before committing it. In the test, one suggestion rewrote a whole long line from Claude's reading of the diff. If a character is wrong, "Commit suggestion" applies the wrong text. Short suggestions are low risk.
  • Cost numbers come from one run per style. Re-measure with a few more runs before relying on the percentages.
  • GitHub's diff limit: PR #1936 has more than 300 files since its merge, and GitHub refuses its diff, so it couldn't be re-run. This is unrelated to styles, but it limits which PRs can be reviewed.
  • The caveman plugin ships its own hooks. That's one reason a review loads only its own style's plugin: caveman never affects the default style.
